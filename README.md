## Запуск

```powershell
.\run.ps1                                   # окно приложения
venv\Scripts\python.exe -m pytest           # тесты (285)

# переснять golden-эталон с текущей PS-версии (после правок core.ps1);
# -SingBox необязателен: без него пропускается только прогон `sing-box check`
powershell -ExecutionPolicy Bypass -File tools\make_golden.ps1 `
    -Core <распаковка ветки ps-1.0.6>\src\core.ps1 -SingBox <путь\sing-box.exe>

# движок для `sing-box check`, если он не в путях по умолчанию:
$env:SING_BOX_EXE = "C:\...\sing-box.exe"

# снимок окна в файл и выход (скриншотная сверка с 1.0.6)
$env:VPN_SHOT = "C:\Temp\shot.png"; venv\Scripts\python.exe app.py

# сборка релиза (этап 6): onedir + portable zip + одиночный установщик
powershell -ExecutionPolicy Bypass -File .\build-app.ps1         # dist\VPNLauncher + zip
powershell -ExecutionPolicy Bypass -File .\build-installer.ps1   # dist\...-Setup.exe
```

Для пользователя: скачать один `...Setup.exe`, запустить (SmartScreen:
«Подробнее» → «Всё равно запустить»), «Установить» — без администратора
и без интернета. Удаление — ярлык «Удалить VPN ЛАУНЧЕР» в меню «Пуск»
или запись в «Программы и компоненты» (тот же файл, `uninstall.exe`).

## Безопасность (пакет S1–S6, 01.10.2026)

- **S1. Подписка в DPAPI.** `subUrl` в `state.json` хранится как `dpapi1:<base64>`
  (DPAPI, user-scope): файл утекает — без профиля пользователя ссылка не поднять.
- **S2. Конфиги под ключ.** `config.json` создаётся под движок и удаляется сразу
  после старта (`purge_config_file`) — креды нод не живут на диске между сессиями.
- **S3. Пиннинг движка.** Перед запуском `sing-box.exe` сверяется по SHA-256
  (только пути по умолчанию; пользовательский путь не блокируем).
- **S4. Гигиена журнала.** Ни подписки, ни кредов нод в `vpn-launcher.log` не
  попадает — закреплено тестами.
- **S5. Kill switch (WFP).** Пока подключены: разрешён трафик с адресов TUN, сам
  движок (его соединения с нодами), LAN/петля/мультикаст; всё остальное
  блокируется — движок упал, туннель рухнул: наружу не утечёт, а LAN жив
  (fail-closed). Сессия WFP открывается с `FWPM_SESSION_FLAG_DYNAMIC` (объекты
  живут до закрытия сессии), снятие дополнительно удаляет фильтры явно по ключу,
  установка начинается с зачистки остатков прошлых запусков. Без админа или без
  адресов TUN — честный отказ (`False` + лог), без подвешивания и без частичной
  установки.
- **S6. Документация.** Ограничения и порядок эксплуатации — здесь и в
  `КОНТЕКСТ.md`.

Осознанные ограничения: пиннинг TLS-сертификатов подписок неприменим (ротация
самих подписок); системный DNS идёт в LAN (фильтровать его — убьём роутер);
ICMP вне слоя ALE может идти мимо kill switch; appid матчится по образу
процесса — в окружении uv `sys.executable` ведёт на пере-экзекцию-заглушку,
поэтому самопроверка берёт путь через `wfp._self_exe()`.

Самопроверка kill switch вживую (права администратора; после инцидента
01.10.2026 — только по явной команде, т.к. трогает сеть):

```powershell
python -m vpn_launcher.win.wfp --selftest
```

## Правило поведения

Поведение VPN обязано совпадать с 1.0.6: конфиги sing-box сверяются по
golden-файлам; `sing-box.exe`, `Setup.cs` и `install.bat` самой 1.0.6 не
меняются — свой установщик портирован отдельно в `installer/` (см. ниже).

### Отклонения от 1.0.6 (все помечены в комментариях кода)

Визуал:

- лампочки при подключении (по просьбе): верхняя у кнопки сворачивания
  горит ровно, нижняя у статуса плавно загорается и дальше пульсирует
  «пик-пик»; при отключении/обрыве обе плавно угасают; при проверке пинга
  нижняя плавно загорается жёлтым и после проверки гаснет (или возвращается
  в зелёную, если онлайн). В 1.0.6 LED статусом вообще не управлялся —
  анимация в `widgets/led.py`;
- подсказка серверов перенесена на строку подписи «СЕРВЕРЫ» — в 1.0.6 она
  перекрывалась с колонкой ПИНГ;
- в попапе пикера свой тёмный скроллбар (`NeonScrollBar`) — в 1.0.6 список
  процессов рисовал нативный белый ползунок;
- пикер (по просьбе): при наборе открытый список не сворачивается при нулевых
  совпадениях — показывает строку «(нет совпадений)» (в 1.0.6 `CloseDrop`);
  заглушку нельзя выбрать кликом;
- окно не исчезает при подключении в TUN (по просьбе, 30.09.2026): в 1.0.6
  не-elevated экземпляр закрывался сразу после спавна повышенного — окно
  пропадало на время UAC и загрузки нового процесса («исчезает и снова
  будто включается»). Теперь перед спавном создаётся именованное событие
  «окно показано» (`win/elevate.py`), позиция окна передаётся аргументом
  `--window-pos=X,Y`, и старое окно закрывается только после `win.show()`
  нового — новое встаёт ровно поверх (та же точка), переход не виден; при
  таймауте 15 с (новое не показалось) — закрытие как раньше. Мьютексы
  обычного и повышенного экземпляров разные (Host.cs), параллельная жизнь
  безопасна; `app.pid` при выходе сносится только если принадлежит себе.

Windows-мосты (на VPN не влияют):

- **автозапуск — новой функции в 1.0.6 нет** (в PLAN-PYTHON.md этап 2);
  обычный HKCU Run, включается/выключается вручную;
- список процессов собран через Toolhelp32 вместо `Get-Process` (без
  psutil) — сверен с `Get-RunningExeList` на этом ПК: идентично 87/87;
- `acquire_instance()` идемпотентен в рамках одного процесса (Host.cs
  одноразовый, такой case там не возникает).

Установка (этап 6, порт `installer/Setup.cs` из 1.0.6):

- рекурсивное копирование (`CopyTree`) — раскладка onedir (дерево
  `VPNLauncher.exe` + `_internal\`), в 1.0.6 копировались только файлы
  верхнего уровня;
- убрана проверка PowerShell 5.1 и пункт «Нет PowerShell 5.1» — PySide6-версии
  PowerShell не нужен (и Python тоже: всё встроено в exe);
- после копирования проверяются `VPNLauncher.exe` + `sing-box.exe` (вместо
  `VPN.ps1`);
- `StopApp` дополнительно гасит `sing-box`, лежащий в целевой папке (чужие
  копии не трогает);
- запасной `vpnlauncher_setup.log` рядом с setup.exe пишется **только когда
  `%TEMP%` недоступен** — в 1.0.6 он писался всегда и оставлял файл там, откуда
  запустили установщик (основной лог всегда в `%TEMP%`);
- SmartScreen: exe не подписан, при первом запуске Windows показывает
  предупреждение «Неизвестный издатель» («Подробнее» → «Всё равно запустить»)
  — как у Setup.exe 1.0.6;
- portable zip и payload установщика собираются из чистой копии: runtime-файлы
  локального прогона (`state.json` с личной ссылкой подписки, логи,
  `cache.db`) в комплект не попадают (`build-app.ps1`, `build-installer.ps1`).

Сеть и потоки (этап 5, тексты/порядок статусов те же):

- загрузка подписки, пинг и запрос внешнего IP идут в `QThread` — в 1.0.6
  это runspace/`DoEvents` (пинг) и синхронный вызов (загрузка); экран не
  подвисает, статусы и их порядок дословно;
- внешний IP: `Invoke-WebRequest` в PS блокировал UI до 8с, здесь фоновый
  поток, надпись «Внешний IP: …»/«Внешний IP недоступен» та же;
- при закрытии окна воркеры ждутся до 2с, затем `terminate` — порт
  `BeginStop` из `FormClosing` (там джоб тоже останавливался принудительно);
- текст ошибки движка `singbox.log.err` читается как UTF-8 (1.0.6 читал
  в системной кодировке).

TUN (починка «TUN не работает», 30.09.2026):

- адрес TUN-инбаунда подбирается из свободных на этой машине
  (`win/tunaddr.py`), вместо зашитого `172.19.0.1/30`. Занятый чужим VPN
  адрес (на машине диагностики `happ-xray` держал `172.19.0.1/30`) ронял
  sing-box на старте: `configure tun interface: set ipv4 address: The object
  already exists`. В журнале приложения этого не видно — `singbox.log.err`
  обрезается при каждом старте (`win/proc.py`), поэтому сбой выглядел как
  «TUN просто не работает». Проверено: тот же конфиг со свободным адресом
  поднимается и живёт;
- первый кандидат пула — исторический `172.19.0.1/30`: без конфликтов
  конфиг совпадает с 1.0.6, golden-эталоны не переписывались;
- подсеть Happ зарезервируется навсегда, пока Happ установлен
  (`win/tunaddr.py::happ_installed`, каталог `FlyFrogLLC\Happ` или ключ
  службы `HappService` в реестре): Happ пересоздаёт свой адаптер при
  переподключении, и в окне между удалением и созданием его адрес
  выглядит свободным — подбор его занимал (журнал 30.09.2026: 01:04:36
  мы на `.5`, 01:05:12 — уже на его `.1`), после чего чужой VPN не мог
  подняться. Детект по установке, а не по процессу: окно пересоздания
  случается при живом процессе. На машине без Happ поведение прежнее;
- выбранный адрес пишется в журнал строкой `tun address: …` — иначе конфликт
  диагностировать негде;
- **`strict_route` выключен** (был `true`, как в 1.0.6): включённый, он
  включает WFP-фильтры, которые **блокируют порт 53 вне туннеля**
  (документация sing-box; проверено вживую: TCP:53 → `WSAEACCES` 10013,
  UDP:53 → таймаут, DNS умирал целиком, пока sing-box жив — и оживал сразу
  после его смерти). А DNS-серверы Windows (роутер, чужой VPN) ходят по
  конкретным маршрутам мимо туннеля. Без WFP они отвечают как раньше;
  DNS-утечка через локальную сеть — та же, что и вообще без VPN;
- **`route_address: ["0.0.0.0/1", "128.0.0.0/1", "::/1", "8000::/1"]`
  вместо авто-маршрута `0.0.0.0/0`**: чужой VPN (Happ) держит свой default
  `0.0.0.0/0` с метрикой 0 и по метрике выигрывал наш — системный трафик
  шёл мимо туннеля (проверено вживую: внешний IP оставался домашним).
  Маршруты `/1` длиннее любого `/0` — наш туннель забирает весь интернет,
  не трогая чужие маршруты; локальные подсети конкретнее и идут напрямую;
  после смерти sing-box его `/1` исчезают вместе с адаптером (нет чёрных
  дыр). Golden-эталоны остаются PS-видом, отклонение нормализуется в
  `tests/test_golden.py::_ps_parity_view`;
- **честный пинг** (`core/latency.py` + `win/routeif.py`): раньше обычный
  TCP-connect с поднятым туннелем принимался локально смешанным стеком
  sing-box — 0–2 мс на любой адрес («пинг врёт»). Теперь не-loopback
  цели привязываются к физическому интерфейсу через `IP_UNICAST_IF`
  (опкод 31, network byte order, `ifIndex` шлюзового маршрута из
  `netsh`), а DNS-разрешение вынесено за замер. Loopback (локальные
  тесты) идёт как раньше;
- **автоперезапуск движка** (`ui/window.py::_on_tick`): 30.09.2026
  sing-box умирал через минуту после старта (exit 1, stderr пуст, событий
  в журнале Windows нет — убит извне), и обрыв оставлял без туннеля до
  ручного переподключения, причём без единой строки в журнале. Теперь
  причина смерти и хвост stderr пишутся в журнал, движок перезапускается
  до 3 раз с тем же конфигом (таймер продолжает работать), после лимита —
  прежняя ветка «Соединение оборвалось…»;
- ограничение: проверяются только адреса интерфейсов, не маршруты чужих VPN;
  при ошибке WinAPI выбор молча откатывается на первый кандидат (1.0.6);
- гипотеза «нет `wintun.dll`» не подтвердилась: sing-box 1.14.2 поднимает
  TUN-адаптер без неё (проверено запуском), файл проекту не нужен;
- проверено на машине с чужим VPN: адаптер `vpn-launcher-tun` поднимается,
  маршруты `/1` забирают интернет-трафик, трафик идёт, после остановки
  маршруты возвращаются, чужой VPN остаётся Up.

Ядро (на поведение VPN не влияет):

- подписка: тело HTTP-ответа сначала декодируется как UTF-8, иначе ANSI
  (1.0.6 через WebClient всегда ANSI/cp1251) — разница видна только в
  display-именах с «сырой» кириллицей;
- запись `config.json`: `json.dumps` вместо `ConvertTo-Json` PS 5.1 —
  формат красивее, семантика та же, `sing-box check` принимает оба;
- текст ошибки `sing-box check`: UTF-8 вместо ANSI-чтения PS 5.1.

### Сохранённые особенности 1.0.6 (не чиним ради паритета)

- vmess: поле `type` из JSON (тип заголовка) в `Get-QueryVal` идёт раньше
  `net` — ws-transport у vmess обычно не строится;
- vmess + tls: `$q` в PS пересобирается только из security/sni/fp/alpn,
  transport теряется совсем;
- обычная (не-b64) подписка, начинающаяся с комментария, в 1.0.6
  склеивается в одну строку и не парсится — фикстура намеренно
  начинается с URI;
- `Select-Object -Unique` для списка direct-apps регистрозависим
  (проверено на PS 5.1) — Python повторяет это.
